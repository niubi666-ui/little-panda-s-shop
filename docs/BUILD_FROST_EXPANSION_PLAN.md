## 1. 目标和范围

- 延续左键 primary 普攻、R键 special 重击、鼠标右键 skill 基础瞬发剑气、Shift 闪避。保留现有冰冻、穿透/分裂、爆炸/寒霜、碎冰追击与乘隙斩。
- 下表保留20项设计及稳定ID；接下来实现剩余15项，每批均可在训练场实际取得、组合、战斗测试。已有五项只做与改动相关的回归。
- 本轮奖励只实现卡牌品质分组、配置和训练模拟抽取，不要求接通正式地图清场奖励、经济、磁盘存档或最终 Boss。重要奖励次数不定死。
- 复用现有剑程序姿态及占位/寒冰表现；逻辑决定命中与区域，特效可替换。不开复杂角色骨骼动画任务，不自动生成 Release 或 commit/push。

## 2. 寒印、冻结与最新精英抗性

已有寒印是独立、有时限、无硬控制的状态。冰冻核心的合法命中可施加寒印，并按原规则请求冻结。寒印能在冻结结束后继续存在；同一玩家刷新而不无限叠层。状态记录施加者、动作、运行时/房间代数、根施放和施加时间。

- 最新决策：游侠使用Boss响应，首次合法申请进入减速窗口，继续当前招式；三次累计保留为其他特殊敌人的可配置抗性。普通怪硬冻结；响应参数和现状见ELITE_RANGER。
- 控制免疫与寒印免疫独立配置；免疫冻结不必免疫标记，但真正死亡、不可选中或阶段无敌不能被强行施加标记。区分训练伤害无敌与游戏中的合法接触/状态许可，不能仅凭零伤害判断。
- 碎冰追击、乘隙斩要求有效冰冻窗口（硬冻结或Boss减速）和更早独立根；寒印及抗冻不能冒充窗口。
- 施加寒印不发布“成功冻结”事实，不触发冰衣/凝霜结晶；标记迁移不计冻结命中数。
- 有效冻结的来源在拒绝刷新时不改变；寒印单独更新自己的来源，不能修改冻结来源。
- 寒印是规则能力，前置检查读取实际执行计划。计划中凭空写标签不授予标记能力。

先保守采用：回锋/追寒同动作互斥；扇刃/双拍互斥；回锋/分裂互斥；破冰重击/普通命中爆炸同动作互斥。扇刃与命中分裂初版也互斥，防止数量乘法。蓄霜先兼容基础、贯穿、回锋，不开放与扇刃/双拍/追寒未经验证的组合。原穿透/分裂、分裂/寒霜规则保留。所有排除对称配置，候选与提交共同校验；不以 UI 隐藏代替执行拒绝。

其余可组合项明确编译顺序，尤其范围宽度、发射数、轨迹、冷却、条件增伤不能因选卡顺序改变结果。新增互斥涉及旧状态时明确报不兼容，不静默删卡。除必要边界外，不强制所有改造只占一个万能槽。

## 4. 分级与房间来源：用户新增决策

用户明确指定：普通小怪房可给普通/稀有；精英给史诗/传说；Boss给传说。目前只需配置分组并在训练模拟，不要自动推进正式路线奖励系统。

已有 `game/data/builds/reward_groups.json`，由 manifest 引用、schema 校验后注入；后续直接扩展该文件，不新建第二份品质表。它集中维护以下字段：

- `schema_version`。
- `rarities`：common/rare/epic/legendary 的稳定 ID、翻译 key、排序。卡片颜色、边框、样式在 Resource 中按 ID 映射，不在 JSON 再写一份表现。
- `upgrade_groups`：upgrade_id → rarity_id 的唯一分配表。每个正常可取得升级恰有一项，不能同时在 prototype.upgrades 中再维护另一份 rarity；调试定义显式排除。不存在或重复 ID 报错。
- `reward_profiles.normal_room`：允许 common、rare；当前相对权重为70/30。
- `reward_profiles.elite_room`：允许 epic、legendary；当前相对权重为80/20。
- `reward_profiles.boss_room`：只允许 legendary。
- `reward_profiles.training_all`：训练专用，允许所有已实现品质；不能被正式房间隐式调用。
- 每个 profile 显式定义候选数量（当前三选一）、品质权重、候选不足策略。以上权重是可调试用初值，不是用户指定的最终概率。

已有卡的品质以该JSON为准；碎冰追击稳定ID是 `shatter_followup`，不新建 `frost_followup`。剩余卡只在执行器、内容校验和可达性完成后加入正常池及品质表。优先保证普通/稀有池能建立核心并满足史诗/传说前置，传说不能要求先有传说才能解锁。

品质为固定分组，本次不为同一张卡另造白/蓝/紫/金四种随机数值版本，也不自动按品质乘全局伤害。rank 和品质独立。修改分组文件即可改变卡出自哪类模拟房间，无需改代码/本地化说明中的硬编码品质名。

### 4.1 抽取与空池

1. app/session 接受明确 reward_profile_id，不从按钮文字/敌人名称推断房间类型。
2. combat Resolver 先给出全部合法操作；rogue 与配置池/品质过滤求交集。
3. 每个候选槽先在仍有合法未选升级的品质中按配置权重选择，再按现有升级权重选唯一 upgrade_id，最后选合法动作绑定。一个升级不因绑定多个动作重复占格或增加品质权重。
4. 品质前置不覆盖战斗前置；Boss奖励不能抽到无法使用的传说，也不能隐式降级普通卡。配置错误与运行时“当前Build没有合格项”分别报告。
5. 合法项不足三个就展示实际数量；零项显示“当前构筑无符合条件的奖励”，允许退出训练面板继续战斗，不无限重抽、不自动塞前置。可另用训练预设建立前置后重试。该短缺策略也写配置，首版实现明确支持的有限策略即可。
6. 锁定offer_id/profile_id/revision/候选操作/品质与RNG；切语言、刷新UI、切面板不重抽。打开中的奖励不可被“切来源”改写，正常关闭再打开重用；专用训练重置须显式失效旧令牌。提交失败不改Build/RNG。
7. 通用fallback也必须满足profile品质和能力条件，不能把Boss传说池偷偷填成power/agility。不需要每组一定保底包含各个品质，只有允许范围与权重；可后续配置保底机制。

## 5. 架构分工

- content：载入并跨表校验扩展定义、状态、效果、品质分组、奖励profile、预设；只读发布。新增效果限于显式字段，不引入JSON脚本。
- combat：Resolver编译和兼容、施放/蓄力状态机、投射物阶段、状态/防护、有限区域、临时物件及技能循环。按职责拆分小执行器，不把20项全塞进一个巨大卡名switch。
- rogue：奖励品质过滤、权重抽样，调用combat提供的合法操作；不处理伤害或冻结。
- app/session：传奖励来源、隔离提交、训练命令、动作与表现组装、房间代数与清理。
- presentation：输入按下/松开/瞄准意图、品质和条件说明、训练面板、表现事实消费。玩家能分辨冻结/寒印/蓄力/防护及触发反馈，不要求最终美术质量。

### 5.1 关键技术边界

- 施放快照与根身份不可变；双拍瞄准与回锋追踪是允许变化的运动输入，不允许在途中读取新Build替换旧伤害。
- 原投射物生命周期要显式分离阶段寿命与根上限。回锋去回段有各自visited及总命中预算；穿透目标稳定排序，墙优先截断；不能新建“无关联第二根”绕预算。
- 蓄力是input intent → charging → committed → recovery，禁止一按先提交普通弹。无卡时不增加延迟；有卡时点按/长按规则在双语UI说明。冷却从成功发射提交开始，蓄力未提交取消不返还或制造已发弹；取消收招沿用动作仲裁。所有玩法时间使用暂停的逻辑时钟。
- 命中前只读查询→确定伤害/待消费状态→确认合法命中→一次性消费并提交→发布事实。标记、护盾、冻结被消费只有一个权威入口；死亡/切房会使计划失效。训练伤害无敌是否消耗状态要明确，初版追击/破冰消费要求正实损，避免无反馈浪费。
- 为状态移除提供有限原因 expired/consumed/death/room_clear 等，迟霜仅订阅自然到期。死亡事件携带必要命中前状态/归属快照，不从已清空Actor反查。
- 临时区域、冰棱、结晶和延迟效果受数量/寿命/采样距离/根预算限制。UI/渲染不做碰撞裁定、不按帧读JSON、不消耗玩法随机制造粒子。
- 减速、防护和增伤通过统一属性/伤害接口合成，不各自set_process(false)或写回基础移速；离开/到期重新从剩余效果计算。
- 新事件声明是否允许派生来源响应，默认只接受指定正式直接来源。死亡传播、资源回复、回响、分裂共享有界规则，不能互相无限喂触发。
