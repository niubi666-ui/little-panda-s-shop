# 项目开发入口

开始开发前先读 PROJECT_CONTRACT.md；玩法参考《小熊猫的小店-项目玩法说明书.md》，美术参考《美术方向基准.md》。用户后续决策优先，同步更新受影响的契约与文档。

## 已确认范围

- Godot项目根目录为game/，对应res://；concepts/与source_assets/位于引擎项目之外。
- 单人PC、GDScript、战斗约70%/店铺约30%、中英文。
- 订单可接0或1张，允许自由下地牢；主店＋可装修小院。
- 元素与构筑主题未定；三幕是首版地图原型，原说明书数量是中期原型目标。长期扩充十几种房间模板及5–6种Boss，不写死幕数、元素枚举或内容池数量。

## 实现约束

- 可调玩法/经济/AI/构筑数值来自JSON；表现资源来自.tres/.tscn。同字段只有一个权威来源。
- 禁止隐藏内容默认值，例如data.get("damage", 25)。缺少必填值应报错；数学恒等元、索引、枚举、技术版本和运行状态初始化可留代码。
- 先校验内容，再解码为只读Definition；由工厂注入模块。禁止在每帧/每次命中读取JSON或通过全局服务定位器取配置。
- 模块以组合实现，命令明确调用，事实用局部signals通知；不使用万能EventBus完成库存/金钱交易。
- combat拥有构筑执行，rogue拥有抽取候选；结算、交付、保存由app/session协调。
- 所有持久库存/金币/订单变更经会话提交入口。使用完全隔离的候选状态，保存失败不改变权威状态。
- 技能由逻辑时间线驱动，动画负责表现；分裂/连锁/持续伤害遵循根预算与来源限制。
- 房间布局、主题、摆放、遭遇和深度曲线解耦；深入总体变难，入房锁定难度与生成方案。玩法障碍需验证可达性，纯视觉随机不消耗玩法随机流。
- 翻译JSON为人工源，生成PO不能手改；玩家可见文本使用key与命名参数。
- 存档使用稳定ID与值，不保存节点引用/翻译名；兼容性问题不能当损坏静默回退。

## 协作与验证

- 每项并行任务声明可写路径、所用接口和验收方法；同一文件同一时刻只有一个写入者。
- 公共契约、schema、project.godot、根场景与导出配置由整合者统一修改。
- 新效果类型或字段先同步契约，内容作者不能假设未实现机制已存在。
- 运行与改动匹配的规则验证、场景验证和必要导出检查。内容加载、随机/叠层、重复交易、双语和存档失败路径优先。
- 交付说明实际改动与已验证项；不要把概念图、架构计划或未运行的示例当成已实现能力。
