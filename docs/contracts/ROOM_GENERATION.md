# 分支路线、奖励节奏与房间生成

2026-10-08。本页记录路线、奖励和房间生成的稳定边界。**已实现独立的短分支内存 Run**：固定5层7节点、两处分叉汇合，每条路径5间简单战斗房；合法选路、成功入房编号、清场回图及生命/测试Build跨房保留。当前API、配置和验证见[路线测试](../RUN_PREVIEW.md)。

当前路线使用人工拓扑与单一灰盒模板，只注入配置的初始测试Build，奖励唯一合法值为`none`。独立[随机地图预览](../MAP_PREVIEW.md)已实现拓扑生成和六类房型展示，不接入选路/战斗；可玩Run的随机拓扑接入、随机模板池、正式Boss、大小奖励及磁盘保存/恢复仍是后续工作。庭院已有的随机物件/组合系统尚未接入此路线入口。

## 1. 节点选路与两层奖励

本节奖励为后续设计目标，不能据此宣称当前路线已经发奖。

- 冒险采用类似《杀戮尖塔》的分支节点地图，玩家选择下一节点；路线图与实际房间布局是两个层次，不等同于八间房串行。
- **大选择**：精英、Boss等关键节点结算后提供能改变构筑的选择，例如动作形态、核心和重要协同；早期“约8次”只是举例，不作为设计目标或生成约束。具体次数、开局是否计入、各节点分配及路线长度后续配置，代码不写死8。
- **小奖励**：普通战斗间穿插纯数值成长的小选择，或材料/其他明确奖励；不自动消耗大选择次数，也不让每只小怪死亡都弹面板。默认以房间/遭遇结算批次发放，频率留待试玩。
- 玩家专精右键或混合发展都应有成长机会；关键池与小奖励池分开配置，不能用小额加伤占掉本应有的大选择。具体池、引导权重、商人/事件的规则本轮不定死。
- 阶段Boss后仍有战斗时，构筑奖励可继续发挥作用；最终Boss后本局结束，不能发放仅对后续战斗生效的无用局内卡。终局采取结算奖励、把最后关键选择前置或继续下一阶段，正式Run设计时确定。
- 训练工具连续三选一仅验证机制，不代表正式奖励节奏。现有开场/每波配置也不是路线系统的权威设计。

## 2. 职责与最小扩展接口

当前content校验路线JSON，rogue按节点生成锁定遭遇，app/session拥有合法选路与提交，presentation显示地图/房间编号。后续按实际需求扩展，不预建空类：

- content提供节点、连接、类型、深度与奖励规则的只读定义；rogue已有独立随机路线预览，未来接入正式路线、模板选择和奖励计划。合法下一节点由app/session依据路线和已提交进度裁定，UI不能代替验证。
- 奖励计划至少能区分major_build/minor_stat/material等职责，并关联稳定node_id、一次性reward_id、内容表引用与结算阶段。字段名在真正实现时确定，不要求当前训练虚构地图节点。
- combat只提供构筑合法性和执行能力，不决定哪一房掉什么。小数值成长仍通过同一合法Build提交，不能另写UI直接改属性；材料未来进入明确的本局收获/库存事务。
- app/session已协调入房、清场、返回地图及死亡；后续接入奖励发布、选择和安全点恢复。重试、重复回调、恢复不能重复发奖，发布后候选与RNG锁定。正式磁盘恢复遵循[会话存档](SESSION_AND_SAVE.md)。
- 当前训练可继续显式使用training奖励来源；未来奖励请求不根据攻击次数、节点名字或界面按钮推断大/小奖励身份。

## 3. 模块化与配置权威

三幕用于原型，十几种布局和5–6种Boss是长期内容池目标，不代表单局长度或固定数组上限。

| 定义职责 | 权威与当前边界 |
|---|---|
| 路线结构与Boss节奏 | 可玩Run的JSON定义固定节点、连接、深度和空奖励；独立预览已有随机图，正式接入与Boss节奏/奖励规则后续扩展 |
| 布局模板 | 当前节点JSON引用template_id，Resource库绑定场景；场景提供出生点/容量及基础碰撞。未来门/合法区域/导航继续由场景定义，不在JSON重复抄坐标 |
| 主题与装饰 | JSON池、兼容/密度/间距；模型/材质/光照用Resource |
| 遭遇与难度 | JSON定义组合、波次、预算、人数/出生约束、深度曲线及倍率上限 |
| Boss池 | 候选、适配竞技场、重复限制和奖励关联 |

一个主题可配多布局、摆放和遭遇；兼容性需校验。当前路线使用人工灰盒出生点；庭院物件在原训练入口使用合法区域摆放，两者目前独立。入口：[路线测试](../RUN_PREVIEW.md)、[房间物件](../ROOM_PROPS_PROTOTYPE.md)、[组合资源](../ROOM_PRESETS.md)、[敌人遭遇](../ENEMY_ROLES_AND_ENCOUNTERS.md)。

## 4. 计划、生成与恢复

当前流程为：校验人工路线 → 按Run seed与node.id锁定遭遇 → 隔离创建房间并检查出生净空/容量 → `commit_enter`成功后增加room_count并激活战斗。失败不消耗房间编号，重复清场/旧房回调不重复推进；跨房保留HP检查点和初始测试Build。当前计划只含节点/模板/深度/类型/空奖励引用及遭遇，未保存磁盘，未声明完整布局恢复。

未来完整生成与恢复流程：

1. 生成路线并验证起终点/分支可达；从节点条件选兼容布局、主题及竞技场。
2. 计算并锁定深度/房型难度快照，按预算与空间约束选遭遇。
3. 放置玩法障碍，验证门、交互点、出生区和战斗通路；再添加纯视觉装饰。
4. 保存可恢复的RoomPlan：稳定ID、版本、实际物件变换、遭遇/出生、难度、奖励引用与玩法随机状态；场景消费方案，不在_ready各自重抽。
5. 正式Run进入/结算经app提交安全点保存；恢复不重生成当前房间、不重新洗牌/发奖。尚未探索节点可延迟细化。

布局、遭遇、奖励/掉落与视觉随机分离；同seed仅在同引擎/算法/内容版本下承诺复现。生成重试有限，失败只能用已验证的兼容回退，无合法方案则报告错误。若订单承诺本局可完成，路线与素材池校验须兑现。

## 5. 深度与验收边界

深度由路线配置定义；回访、重载、恢复不重复推进，不从场景名/主题推断。`node.id`是身份，`layer/column`是地图位置，`depth`是难度输入，`room_count`是成功入房次数；这些字段各有职责。当前房间编号只在成功入房提交后增加，准备、失败和重复回调不增加。后续允许缓冲/休息节点，总体随深入提高压力；不按玩家刚拿到的Build偷偷增强现存敌人。

优先增加敌人配合、波次与招式压力，生命/伤害倍率有界；同时约束敌人数、远程比例、出生空间和预警可读性。不同分支长度与休息节点是否增加深度须由路线配置明确。

当前短图已验证合法选路、编号、入房失败隔离、生命/Build跨房、清场/死亡/重开和出生净空；实际结果见[路线测试](../RUN_PREVIEW.md)。这不等于已验证大小奖励、随机模板或磁盘恢复。

后续按切片增加少量布局、大小奖励和正式安全点：验证出生/出口及战斗通路可达、视觉随机隔离、奖励幂等和重载一致后再扩池。Boss/竞技场不匹配、超容量、无合法计划、回退失败及中断恢复需有针对性验证；重要Build选择次数由后续试玩确定，不约束当前地图预览，也不代表当前5房测试路径已实现奖励。
